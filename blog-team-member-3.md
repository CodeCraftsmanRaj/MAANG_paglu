# Turning a Retrieval Engine Into Something You Can Actually Use

## The API was ready. The product wasn't.

Long before there was a finished UI, the backend could already do impressive things: hybrid keyword + vector + graph retrieval, eight different answer formats depending on project type, role-scoped visibility on every fact. But a retrieval engine behind HTTP endpoints is not a product. A user looking for "how is deployment configured?" needs a search box, a project picker, an answer with its sources — and a reason to trust what comes back.

My job was to turn that engine into something a person could operate without reading a single API doc.

## Making permissions feel like a feature

The server enforces access control on every query: each fact carries tags, each role carries allowed tags, and facts outside your clearance simply never reach you. The risk with invisible security is that users can't tell "we found nothing" apart from "you're not allowed to see this" — and admins can't verify that restricted answers really are restricted.

So permissions became a visible part of the UI:

- **Role switching ("Viewing as")** — a custom-built dropdown (no native selects) that lets an admin preview exactly what a member or a scoped role would see, sent as an `X-View-As` header that the server validates. Flipping roles changes results live, which makes the access model tangible instead of theoretical.
- **Provenance sentences** — every answer item renders a human sentence like "From a pasted note, in Default Workspace, recorded 3 days ago," generated by a dedicated formatter module with its own unit-test suite. When a caller lacks clearance, the backend redacts the source, and the UI shows "From a restricted source." Trust comes from always being able to ask "where did this come from?"

## Guiding people through the workflow

The app has three main views — Capture, Find, and Team — and each had usability questions hidden inside it.

Capture accepts pasted text, URLs, files, and drag-and-drop onto the main canvas. Find needed a scope picker: a hierarchical tag tree with filter and add-new-tag support, so users can narrow retrieval to their domain instead of the whole workspace.

The biggest UX gamble was project classification. Every project gets a retrieval paradigm (RAG, ruleset, key-value, denylist, versioned, graph, allowlist, keyword). Expecting users to know which one they need was unrealistic. The create-project modal therefore offers "Auto-classify via AI" as the default — the backend's LLM looks at the project name and a sample of content and picks the mode, with the reason shown back to the user. Manual override stays available in a dropdown for people who know better.

The desktop question had a surprisingly light answer. Electron turned out to be a thin shell: one main-process file that opens a window, loads the same React app, and handles the one thing a browser can't do well — screen capture. Electron lets us register a display-media handler that automatically supplies the first screen, so "Watch my screen" runs without a picker dialog interrupting the flow every 20 seconds.

## The one that got away: config for humans

The recurring friction was configuration. The frontend resolves its API base at build time (`VITE_API_URL`), falls back to the vite dev proxy in development, and Electron can point at any hosted UI via `APP_URL`. That works, but it meant every deployment target needed a rebuild — including our own, when we pointed the production build at the deployed AWS API Gateway URL. A settings surface for non-developers is the obvious next step, and I'd design it in from day one next time.

## Shipping without breaking the working thing

The production build needed to hit the AWS API while local development kept working unchanged. The solution was layering: the production env file bakes the deployed API Gateway URL into the bundle; the dev setup keeps using the same-origin proxy to localhost. Verifying the built bundle contained no localhost references became a release checklist item, and the AppImage packaging (via electron-builder) gave us a runnable Linux artifact for demos. The pattern that mattered: never make production the enemy of local development, or nobody builds locally anymore.

## What I learned

The backend's guarantees — RBAC on every query, provenance on every fact — only became real when the interface made them visible. Most of my best UX decisions were translations of backend behavior into UI: a security model became a role dropdown; source tracking became a sentence under every answer. And the discipline that paid off most was keeping one codebase honestly serving three surfaces — vite dev server, hosted web build, Electron desktop — from a single API client module.
